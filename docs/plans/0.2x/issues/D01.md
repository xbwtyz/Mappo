# [D01] Evaluate unified and persistent edit history across Mappo workspaces

> **Published tracking proposal:** [#106](https://github.com/xbwtyz/Mappo/issues/106) records this limitation or possible capability. This is **not** an approved implementation or assigned release.

**Group:** D · **Classification:** Confirmed history scope limitation · **Suggested priority:** P2 · **Version:** Unassigned

## Current behavior and user impact

Undo/Redo is session-only and operations from different editors can invalidate incompatible histories; history disappears after load.

**Current technical limitation:** Editors have bounded, scoped histories; road history defaults to six entries and snapshots coupled transactions.

## Reproduction / evidence collection

Edit a road, then restructure a property or reload a saved project; check which Undo entries remain available.

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Choose whether users need a global, cross-editor Undo stack and/or persistent revision history, without losing atomic invariants.

## Draft acceptance criteria

- [ ] First decide whether global history, persistent history or both are goals.
- [ ] Specify transaction fingerprints, full-city revision checks, memory bounds and schema implications.
- [ ] No replay of an edit over incompatible accepted state or a stale ownership mapping.
- [ ] If persisted, verify safe load/recovery and bounded file growth; previous scoped behavior remains predictable.

## Dependencies and design boundary

A/B/C engine models may alter transaction definitions; design after those stabilize.

**Owner decision needed:** Recommended: design unified session history separately from persistent history; do not promise both in one milestone.

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
