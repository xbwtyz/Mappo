# [C01] Support compound connected and detached building components

> **Published tracking proposal:** [#104](https://github.com/xbwtyz/Mappo/issues/104) records this limitation or possible capability. This is **not** an approved implementation or assigned release.

**Group:** C · **Classification:** New capability / current design restriction · **Suggested priority:** P2 · **Version:** Unassigned

## Current behavior and user impact

Building shape operations cannot freely combine detached wings, arbitrary unions or nested courtyard islands into a single structure.

**Current technical limitation:** Connected rectangular wings, vertex editing and valid courtyard rings are supported; disconnected components and boolean unions are out of scope.

## Reproduction / evidence collection

Attempt to attach a detached wing as part of one building, or create a nested courtyard/island structure.

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Extend building structures while maintaining ownership, area, access, selection, rendering and validation consistency.

## Draft acceptance criteria

- [ ] Choose a precise geometry representation and distinguish separate buildings from one compound building.
- [ ] All components remain inside owned property/plots and have defined access/frontage policy.
- [ ] Preview/Apply/Undo/Redo and project files preserve unknown metadata and authored geometry.
- [ ] The 2D model stays authoritative and suitable for future derived 3D views.

## Dependencies and design boundary

B01/B04 flexible property and plot containment may simplify this work.

**Owner decision needed:** Do multiple detached components really need one building ID, or should they be separate linked buildings?

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
