# [C02] Support multiple building-topology operations per draft transaction

> **Draft only:** Proposed future GitHub Issue. No GitHub Issue has been created yet.

**Group:** C · **Classification:** Confirmed editing restriction · **Suggested priority:** P2 · **Version:** Unassigned

## Current behavior and user impact

A user must Apply between operations such as adding a wing, inserting a vertex and adding/removing a courtyard.

**Current technical limitation:** `this.topologyChanged` blocks a second topology operation in the same direct edit session, while coordinate moves can accumulate.

## Reproduction / evidence collection

Begin a direct-building edit, insert a vertex, then try adding a wing before Apply.

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Let a user make several validated structural changes before one Apply and Undo step.

## Draft acceptance criteria

- [ ] Support a bounded sequence of compatible topology operations without corrupting handle indices or hole identity.
- [ ] Recompute validation after each step and immediately before Apply.
- [ ] Cancel discards the complete session; Apply commits once; Undo/Redo restores exactly.
- [ ] Both browsers correctly update tool state, selected geometry and errors.

## Dependencies and design boundary

Existing F1/F2 edit state and history; useful standalone improvement, not a prerequisite for B01.

**Owner decision needed:** Start with a small maximum sequence and allow full reset; require a clear definition of multi-operation history.

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
