# [A02] Evaluate support for multiple disconnected street networks

> **Draft only:** Proposed future GitHub Issue. No GitHub Issue has been created yet.

**Group:** A · **Classification:** Deliberate rule / feature expansion · **Suggested priority:** P3 · **Version:** Unassigned

## Current behavior and user impact

The road engine requires one connected network, so separate islands of roads cannot be accepted in one city.

**Current technical limitation:** `disconnected-graph` rejects multiple components; the generator and dependent property/frontage model assume a connected network.

## Reproduction / evidence collection

Construct two valid but disconnected ordinary road components inside the city survey; graph validity fails.

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Define whether isolated road networks are useful, and if so support them without creating unsupported ownership or access.

## Draft acceptance criteria

- [ ] Document one genuinely useful user scenario and whether a disconnected component is intended to be legal.
- [ ] If approved, make connectivity semantics explicit for blocks, parcel frontage, roads-to-gates/bridges and path access.
- [ ] Isolated orphan nodes stay invalid; no silent abandonment of protected or authored data.
- [ ] Portable save/load, Undo/Redo and both browser engines preserve component identities.

## Dependencies and design boundary

A01 first; separate design/schema review may be required for access semantics.

**Owner decision needed:** Should a city legally have disconnected roads, or is connectedness an essential invariant that we retain?

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
