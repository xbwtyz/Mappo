# [A03] Extend road intersection normalization for coincident and collinear contacts

> **Draft only:** Proposed future GitHub Issue. No GitHub Issue has been created yet.

**Group:** A · **Classification:** Confirmed documented restriction · **Suggested priority:** P1 · **Version:** Unassigned — after 0.2.1

## Current behavior and user impact

Some seemingly valid intersections fail because overlapping streets, coincident corners or multi-contact junctions cannot be reconciled safely.

**Current technical limitation:** Crossing normalization rejects collinear overlaps, pairs of existing coincident endpoints, and multiple contacts at one existing junction.

## Reproduction / evidence collection

Attempt street connection edits producing one of the rejected collinear/coincident cases; record exact offending edge IDs and safe expected topology before coding.

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Support more complex but valid intersections with deterministic endpoint/edge identity and unambiguous graph/faces.

## Draft acceptance criteria

- [ ] Positive fixtures for each approved crossing class result in a deterministic planar graph.
- [ ] Overlapping but truly ambiguous or zero-length configurations still fail with useful diagnostics.
- [ ] Matched block, district, parcel and road IDs are preserved whenever continuity can be proved.
- [ ] Edits support preview, Cancel, atomic Apply, Undo/Redo and offline save/reopen in both browsers.

## Dependencies and design boundary

A01 road-face semantics and A06 local topology ownership.

**Owner decision needed:** Which crossing subtypes should be normalized, and which must remain invalid (e.g., stacked bridges or overlapping lanes)?

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
