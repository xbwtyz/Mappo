# [A04] Design controlled editing of protected road connections

> **Published tracking proposal:** [#96](https://github.com/xbwtyz/Mappo/issues/96) records this limitation or possible capability. This is **not** an approved implementation or assigned release.

**Group:** A · **Classification:** Deliberate safety boundary / feature expansion · **Suggested priority:** P2 · **Version:** Unassigned

## Current behavior and user impact

Boundary, bridge, bank, gate/defense, plaza and pass links cannot be restructured through ordinary tools.

**Current technical limitation:** Protected road/junction guards reject modifications; this is correct safety behavior, not a defect.

## Reproduction / evidence collection

Try to move/reconnect a junction incident to a protected edge; observe `protected-junction` or protection errors.

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Add separately scoped protected-infrastructure editing with verification of the linked water, defense, boundary and access records.

## Draft acceptance criteria

- [ ] Enumerate which protected operation is authorized; retain default rejection for others.
- [ ] Proposed change includes linked infrastructure, districts, access and dependent authored records in one impact ledger.
- [ ] No protected structure is silently deleted, crossed, orphaned or regenerated.
- [ ] Approved operation has independent validation, atomic rollback and covered save/reopen behavior.

## Dependencies and design boundary

A01/A03 road topology plus domain-specific water/fortification contracts.

**Owner decision needed:** Start with exactly one protected connection class, if any; retain the general protection rule.

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
