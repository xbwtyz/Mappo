# [A06] Expand bounded road topology reflow for large changes and ambiguous face ownership

> **Draft only:** Proposed future GitHub Issue. No GitHub Issue has been created yet.

**Group:** A · **Classification:** Confirmed architectural limit · **Suggested priority:** P1 · **Version:** Unassigned — after 0.2.1

## Current behavior and user impact

Larger topology edits or district/land-use changes can be blocked because the engine cannot safely identify every replacement block or its ownership.

**Current technical limitation:** `TOPOLOGY_BLOCK_LIMIT = 32`; complex face matches and mixed district/usage groups fail closed.

## Reproduction / evidence collection

Design a valid multi-block topology change affecting more than 32 blocks, or crossing differently classified blocks; record affected IDs and actual failure.

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Support larger well-defined changes with auditable successor lineage, bounded computation and explicit choices for ambiguous ownership.

## Draft acceptance criteria

- [ ] Distinguish unsafe ownership from arbitrary hard-count limits; define supported scale and measured work budgets.
- [ ] Preserve verified unchanged blocks and authored properties; create explicit old-to-new lineage for changed faces.
- [ ] Require decisions rather than guessing for district/usage and user-authored conflicts.
- [ ] Validate full city and portable project before atomic Apply; old negative fixtures remain rejected.

## Dependencies and design boundary

A01 and A03; B01/B05 may be required for complex parcel reflow.

**Owner decision needed:** Which specific topology-changing task currently fails but should succeed? Get a reproducible fixture before implementation.

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
