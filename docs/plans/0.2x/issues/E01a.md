# [E01a] Assess larger portable project imports beyond 20 MiB

> **Published tracking proposal:** [#109](https://github.com/xbwtyz/Mappo/issues/109) records this limitation or possible capability. This is **not** an approved implementation or assigned release.

**Group:** E · **Classification:** Explicit import limit / scale proposal · **Suggested priority:** P3 · **Version:** Unassigned

## Current behavior and user impact

Portable project files larger than 20 MiB are rejected before reading. Exactly 20 MiB is accepted when the project passes validation.

**Current technical limitation:** `readProjectFile` enforces the inclusive `MAX_PROJECT_BYTES` limit.

## Reproduction / evidence collection

Open a valid-format `.mappo.json` at 20 MiB, then try the same file at one byte over.

The D03 audit verified both boundary cases with whitespace padding in offline Firefox and Chromium on `0.2.12-dev`. The largest of 24 generated project saves was 4.22 MiB. The padded fixture verifies the byte cutoff. A capacity decision needs evidence from a representative project that hits the cap.

## Desired outcome

Measure realistic project sizes and consider safe larger or streaming imports with memory and validation safeguards.

## Draft acceptance criteria

- [ ] Define observed real-world demand, file sizes and browser memory budgets.
- [ ] Keep reject-before-mutate security and project integrity guarantees.
- [ ] If capacity increases, bound parsing, validation, recovery size and cleanup under failure.
- [ ] Test in Firefox/Chromium without network or server dependencies.

## Dependencies and design boundary

D03 capacity audit and schema/storage policies.

**Owner decision needed:** Is this a practical user limitation now? Favor evidence before raising the cap.

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
