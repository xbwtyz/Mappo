# [A01] Support connected dead-end roads after segment deletion

> **Existing issue:** [#79](https://github.com/xbwtyz/Mappo/issues/79). The approved specification is published on Issue #79; this is a planning reference, **not** a new issue to file.

**Group:** A · **Classification:** Confirmed bug / engine gap · **Suggested priority:** P0 · **Version:** 0.2.1 — committed target · **Architecture choices:** Owner approved A/A/A/A; implementation not yet approved

## Current behavior and user impact

Deleting an ordinary street segment is blocked when the surviving connected branch terminates at degree-one junction, even when a useful cul-de-sac/dead-end would remain.

**Current technical limitation:** Graph validation emits `dangling-junction` and face extraction expects bounded simple rings; deletion cannot safely reflow adjacent development.

## Reproduction / evidence collection

Select an ordinary segment whose deletion leaves another connected segment ending at an interior junction; choose **Roads → Change street connections → Preview removal**; the original report showed `Junction N-0195 ends without a closed city face` (seed and segment not captured).

Reconfirm against the version planned for implementation, recording a deterministic seed, relevant IDs, browser and actual error message. The source reference indicates an implementation restriction, **not** that a user test was independently executed for this candidate.

## Desired outcome

Allow a connected terminal street to remain, with its footprint/corridor represented for block and parcel clearance.

## Draft acceptance criteria

- [ ] The surviving ordinary stub remains connected and renders during preview and after Apply.
- [ ] Bounded block faces and merged parcels remain valid; terminal corridor and setbacks stay free of property/building encroachment; **no new frontage/access along dead end**.
- [ ] Protected routes, isolated roads, unsafe authored or unknown parcel ownership and impossible placement remain blocked with actionable reasons; only proven generated untouched development adapts.
- [ ] Cancel/Reset leave the accepted city unchanged; one Apply is atomic; Undo/Redo and portable save/reopen preserve topology, clearance, IDs and metadata.
- [ ] Regression suite covers valid and invalid cases across four morphologies, Small/Large city fixtures, and Firefox/Chromium desktop offline HTML.

## Dependencies and design boundary

Existing Issue #79. Foundation for future A03/A06 topology changes.

**Approved decisions (D-021-1–4 = A/A/A/A):** 0.2.1 supports connected ordinary **interior** stubs resulting from otherwise-supported segment deletion only; retain corridor and setback **without introducing new frontage/access**; adapt only verified generated untouched records, preserving authored/unknown data; implement through one PR with internal P1–P4 checkpoints. See the [approved replacement published to existing Issue #79](../ISSUE_79_UPDATE_DRAFT.md). No new issue should be created.

## Preservation and verification gates

Retain deterministic generation, one authoritative accepted city, preview/Cancel isolation, independent full validation before atomic Apply, stable provable identities, protected and unknown authored metadata, appropriate scoped Undo/Redo, and safe offline project round-trip. Any required schema migration, existing CI policy change, release or Pages publication needs **separate authorization**. Use targeted tests during development and full six-runner CI for the review-ready PR.
