# Mappo 0.2.x — Smart Frontage Snapping

**Scope:** D-SFS-1..6=A owner approved. P1–P5 approved for a focused implementation. Branch `feature/mappo-smart-frontage-snapping` is dependent on PR #128's current head because that foundation fix is still awaiting separate merge authorization. Do not merge, publish a Release, tag or deploy Pages without independent approval.

## User outcome

Dragging a corner of the single frontage edge on a 5–12-vertex property projects it onto its assigned street's line. Dragging the visually distinct midpoint translates both frontage endpoints rigidly. Illegal movement stops at a reachable validated position. Numeric coordinate editing and keyboard nudges share the same constraints.

## Invariants and engineering decisions

- D-SFS-1=A: Resolve the property's assigned road from current block/road/node topology, never silently switch streets on corner lots. Fail closed on detached or unresolvable road geometry.
- D-SFS-2=A: Drag one frontage endpoint along a line through the other endpoint. Keep opposite endpoint fixed.
- D-SFS-3=A: Add a frontage midpoint handle for rigid parallel translation with fixed length and unchanged road assignment.
- D-SFS-4=A: Retain the independent property validator; project target coordinates then inspect the swept candidate and clamp at the first blocked interval, using bounded subdivision. Do not mutate neighboring plots, buildings or accepted geometry.
- D-SFS-5=A: Existing draft/Apply/Reset/Cancel/Undo/Redo/portable-save contracts are authoritative; no new schema or persistent snapping state.
- D-SFS-6=A: This milestone targets irregular polygon edits first. Preserve other four-sided and road-editing behaviors.

## P1–P5 checkpoints

- **P1 geometry:** pure road direction, length and projection; actual road direction replaces historic frame-angle drift in edited-frontage inspection. Unchanged accepted frontage retains its prior exception.
- **P2 gesture/UI:** constrained corner pointer movement; midpoint handle, inline feedback and guide; drafts only.
- **P3 collision:** bounded swept validation with unchanged independent Apply gate. A previously invalid baseline remains blocked until its issues are resolved.
- **P4 precision:** numeric and keyboard operations respect the same policy; history, metadata, building and plot invariants.
- **P5 verification:** deterministic geometry and integration tests; Firefox and Chromium property browser coverage; offline HTML build and artifact parity; six-runner exact-head PR CI.

## Deliberate limitations

- This is not a road-assignment switcher or arbitrary multi-street frontage model.
- No automatic neighbor/building relocation, authored plot retiling, or road geometry change.
- The bounded swept sampler is intended for local direct-manipulation gestures, not a global optimal pathfinder around non-convex obstacles; independent Apply always remains authoritative.
- No additional mobile QA, heavy C7 performance gate, save schema change or forced tutorials.

## Acceptance

- At least one geometry fixture proves each endpoint projects and the unchanged endpoint stays fixed; minimum frontage 7.
- Midpoint movement maintains alignment, orientation, frontage length and assigned street.
- No invalid preview can be accepted or saved through snapping; no accepted city mutation before Apply.
- Historic frame-drift fixtures remain valid and never rewrite frontage on pointer-down.
- Numeric editing, portable save/open, scoped Undo/Redo, Restore frontage and Cancel/Reset pass.
- Existing polygon, plot, building and road workflows still pass.
- All required Node/browser CI and aggregate gate are green at exactly the PR head.
