### Identity and history audit — regeneration blocker

- `src/editor/property-creation-e1.js:130–139` and `src/editor/property-split-e2.js:20–27`: allocate next numeric ID using only currently existing rows. Removing the highest number permits its later reuse. Split also derives plot IDs from live inventory plus fragments within the current operation.
- `src/editor/plot-draft-027.js:31–34` and `src/editor/property-edit.js:125–131`: choose first unused plot number from current/draft inventory. A deleted gap is reusable.
- `src/editor/building-structures.js:65–72,119–120`: random BLD-MAN identifier checked against current records; explicit add accepts unused prefix. Does not prove historical nonreuse.
- `src/generators/buildings.js:169–175,264`: procedural sequential property/plot/building IDs; generation IDs cannot simply be reused as regeneration IDs.
- `src/core/accepted-edit-history-d01.js`: history is session-only, 20 entries/64 MiB default, prunes older transactions and drops redo after branching; canRecord()/fits() must preflight recovery. Existing oversize behavior is not suitable for destructive Apply.
- `src/data/project-format.js`: portable envelope has document identity and extensions but no reviewed persistent allocator/retirement contract. City ID is seed-derived (`src/core/city-model.js`), not a unique incarnation counter. Need explicit host/session identity in later worker protocol.

Current inventory and bounded history cannot prove durable no-reuse across retirement, history pruning, undo branches and save/reopen. Deterministic allocation from an identical accepted state can repeat an earlier ID when the prior ID is no longer recorded. A new namespace can avoid collisions with existing numeric generators but cannot alone prove historical uniqueness inside its own namespace. Do not enable regeneration. Owner review is required before a persistent allocation ledger/high-water-mark contract or a weaker probabilistic-uniqueness policy; no schema, portable envelope, workspace or allocator changes are made here. Consider a monotonic persisted recovery sequence and isolated typed IDs, with explicit Undo/Redo and portable reopen semantics; schema/version implications require separate approval after design review. E1 remains draft and all prior tests/strict behavior preserved.

## Owner-approved parallel-execution readiness

Decision recorded November 25, 2026 (Pacific). The owner approves preparing Mappo for future multithreading during SRE, rather than implementing a general worker pool or parallelizing the entire engine now. This supplements SRE-01, SRE-07, SRE-08, SRE-10 and SRE-11 without changing their acceptance requirements, the existing Schema 11 contract or the approved delivery sequence. Preserve the already-approved offline worker execution of expensive SRE work; this decision does not postpone it.

### Design constraints for current SRE work

- Keep computation independent of DOM, UI state and accepted-project mutation. Prefer deterministic functions over detached immutable inputs and explicit intent, policy, seed, revision, budget and dependency context. Keep task boundaries and result contracts explicit and serializable; avoid speculative abstractions without a current use.
- Preserve a single authoritative accepted-city writer. Workers may produce detached proposals and provisional reservations, never publish accepted changes, commit allocation counters, alter history or authorize Apply. Use Schema 11 independent identity/transaction verification, exact reviewed candidate authorization and atomic chronological publication. No shared writable city memory.
- Keep candidate ranking, tie breaks, enumeration and aggregate work limits independent of worker completion order. A future scheduler must retain strict incumbents, preserve strategy priority, prevent double-spending work budgets and reject stale results by project instance/revision, intent, policy and request identity. Cancellation, Stop, Continue and Reset retain their approved semantics.
- Keep transport compact and typed, with explicit ownership of any transferred buffers and no unnecessary project copies. Do not add a server, required network access, cross-origin isolation requirement or SharedArrayBuffer dependency. Preserve desktop Firefox/Chromium offline file:// and deterministic standalone build behavior.
- When a current SRE task admits an independent computation boundary, keep it separable and testable. Continue current domain integration and qualification; no mandatory general-purpose scheduler, parallel rewrite, new schema, new feature gate or performance optimization campaign is implied.

### Deferred implementation and evaluation

1. Finish the approved SRE roadmap and integrated qualification. Record representative end-to-end timings, search versus Apply costs, main-thread responsiveness, memory and transport costs as part of existing measurement obligations; no new exhaustive optimization campaign is required.
2. After SRE completion, identify sufficiently independent expensive workloads and propose a separately reviewed milestone for a bounded reusable Web Worker pool and deterministic task coordinator. Start with SRE candidate search/packing if profiling justifies it; compare against the single-worker baseline. Selectively expand to geometry validation, generation, spatial indexing, export or derived 3D mesh work only where measured benefit warrants complexity.
3. Future implementation approval must cover worker count/capacity policy, scheduling, cancellation and crash recovery, snapshot/transfer ownership, deterministic reduction, global budget partitioning, identity and transaction safety, offline compatibility and measurable acceptance. Require same accepted results and protected-data behavior for the same seed/intent and fixed work policy across worker counts/completion orders, no stale publication or identity reuse, unchanged history semantics, bounded memory, and measured performance rather than promised speedups.

Status: readiness direction approved; general worker-pool implementation and broader parallel execution deferred and not authorized. No release, merge, version or format change follows from this decision.
