## Definitive production reconciliation lifecycle

1. Create immutable editing intent.
2. Validate topology and discover dependencies.
3. Direct validation.
4. Strict B1 reconciliation.
5. Selective adaptive reconciliation.
6. Enhanced adaptive reconciliation where justified.
7. Retain best independently validated preservation candidate.
8. If preservation fails, provide structured review.
9. Offer explicit demolition search only when eligible.
10. Present exact reviewed destructive candidate and removal set.
11. Obtain explicit authorization for that candidate.
12. Independently validate before Apply.
13. Commit one atomic city transaction.
14. Support exact Undo/Redo.

A failed later strategy must not discard a previously validated incumbent for the same intent and revision.

A cancelled or stale intent must never apply its candidate.

Demolition is not an automatic search tier.

## Approved implementation checkpoint P1 — Architectural foundation

### P1.1 Operation adapter

Separate road-specific intent from reusable reconciliation orchestration.

The operation carries the following data.

- Accepted project identity and revision.
- Operation type.
- Edited IDs.
- Proposed geometry.
- Affected dependencies.
- Authorized transformations.
- Strategy configuration.
- Computational limits.

Only connected road translation is integrated in B1R.

### P1.2 Internal strategy registry

The registry defines five strategies.

- Direct validation.
- Strict reconciliation.
- Selective adaptive.
- Enhanced adaptive.
- Demolition recovery.

Keep independent finalization authoritative and outside strategy control.

Strategies declare identity, version, supported operation, preconditions, required capabilities, budget usage and candidate/diagnostic outputs.

The registry remains internal.

### P1.3 Constraint descriptors

Organize existing authoritative validators around containment, separation, rigidity, ownership, connectivity, attachment and protection.

Hard constraints never become optional scoring penalties.

Do not build a universal mathematical solver.

Elevation is only a future extension point.

### P1.4 Capability policy

Extend existing policy classification for fixed, rigid, deformable, dependent, protected, unsupported and decision-required objects.

Demolition is a separate capability, not implied by movability.

Unknown geometry and unrecognized dependencies default to protection.

### P1.5 Spatial context

Track scope by record role.

- Edited objects.
- Authorized reconciliation objects.
- Observable dependencies.
- Unaffected records.

Provide reusable spatial query interface using existing lookups and geometry primitives.

Do not implement automatic cross-block modification or a full new shared spatial-index system.

### P1 gates

- Existing behavior retained during refactoring.
- Strategies cannot bypass validators or capabilities.
- Unknown objects fail safely.
- Deterministic, read-only context.
- No schema changes.
- Authored/protected/dependent structure tests pass.

## Approved checkpoint P3 — Orchestration and demolition recovery

### P3.1 Progressive orchestration

Execute the preservation strategies progressively.

Retain validated incumbents across strategies.

Do not sacrifice an accepted preservation solution merely because another strategy fails.

### P3.2 Preservation computational limits

The operation uses the following ceilings.

- Selective allocation: 4,000,000 work units.
- Enhanced allocation: 4,000,000 additional work units.
- Total adaptive preservation work: 8,000,000.
- Total state expansions: 32,768.
- Beam width: 8.
- Retained candidates per parcel: 24.
- Retained candidates per building: 24.
- Affected parcels: 256.

Shared operation-wide accounting. No hidden resets.

Meter preparation, spatial queries, geometry, compatibility, access repair and finalization.

Existing impact-analysis and independent verification allowances remain separately bounded.

Timing controls scheduling, not candidate selection.

### P3.3 Demolition eligibility

A building must satisfy every eligibility condition.

- Recognized generated building.
- Generated adaptive parent parcel.
- Supported canonical geometry.
- Within authorized reconciliation scope.
- No protected authorship.
- No courtyard dependency.
- No compound membership.
- No unsupported geometry or metadata.
- No unrecognized reference or protected relationship.

Never permit demolition of authored buildings, buildings on authored parcels, protected or dependent structures, unknown records, parcels, plots, roads or infrastructure under this milestone.

Derive eligibility independently from the current accepted project.

### P3.4 Hybrid demolition search

Only run after explicit user request following preservation failure.

Run these stages in order.

1. Prioritized singleton removal.
2. Prioritized two-building combinations.
3. Progressive obstruction-first removal.
4. Complementary progressive largest-first removal.
5. Explicit deeper search if requested.

Use live solver diagnostics as ranking hints, not proof of causation.

Dedupe exact removal sets.

Prefer fewer removals, then lower demolished area.

No automatic clear-all strategy.

No automatic replacement.

### P3.5 Destructive candidate objective

Compare destructive candidates in this order.

1. Number of demolished buildings.
2. Total demolished building area.
3. Number of surviving buildings moved.
4. Surviving building displacement.
5. Surviving building rotation.
6. Parcel deformation.
7. Plot deformation.
8. Access changes.
9. Deterministic tie-break.

Report the best independently validated solution discovered within the search budget.

### P3.6 Approved demolition computational limits

- Distinct removal subsets per search: 16.
- Normal removal depth: 8 buildings.
- Explicit deeper-search depth: 16 buildings.
- Work per subset: 4M.
- Shared demolition work per intent: 32M.
- Shared demolition expansions: 131,072.

Deeper search consumes remaining shared allowance and does not silently reset budgets.

Preservation and demolition share a 40M adaptive ceiling per intent. Impact analysis and verification have separate bounded allowances.

Demolition search must not run automatically during dragging.

### P3.7 Independent original-to-candidate validation

Research used reduced-input clones. That is insufficient for production.

Implement an independent gate comparing the original accepted project directly with the complete proposed candidate.

The independent gate verifies each requirement.

- Exact removed IDs match reviewed removal set.
- Every removed building remains eligible.
- No unrelated record disappears.
- Surviving identities and authorized geometry preserved.
- Only permitted membership, provenance and derived-reference changes occur.
- Protected records and relationships unchanged.
- Topology, geometry, access and stored-project validators pass.
- Original project remains unchanged until Apply.

Permission to explore demolition is not permission to execute demolition.

- No lost validated incumbent.
- Zero unauthorized or protected removals.
- Zero duplicate subset evaluations.
- Zero budget violations.

## Approved checkpoint P4 — Responsiveness, diagnostics and UX

### P4.1 Resumable execution

Make these operations resumable.

- Parcel candidate generation.
- Building placement.
- Compatibility checks.
- Access routing.
- Preservation verification.
- Candidate finalization.

Provide worker-compatible interface, but defer a dedicated worker.

### P4.2 Cancellation and revisions

Tie sessions to accepted revision, intent and configuration.

Invalidate active reconciliation when any of the following changes occur.

- User changes movement.
- Edit is cancelled/reset.
- Project is loaded or replaced.
- Undo/Redo occurs.
- Permissions change.

No stale preview publication or application.

### P4.3 Structured failures

Report a distinct result for each failure category.

- Topology invalid.
- Geometric conflict.
- Search exhausted.
- Work limit.
- Protected object.
- Scope conflict.
- Unsupported geometry.
- Decision required.

Include implicated IDs, relevant measurements and actionable explanations.

Correct the setback diagnostic measurement issue.

Use existing hover-over error and Inspector conventions.

### P4.4 Demolition UX

Integrate into existing map-centered Inspector/review workflow.

Use the following review flow.

- Preservation failure explained.
- Explicit “Explore demolition options” action.
- Cancellable search with truthful progress stages.
- Preview exact removal set.
- Highlight removed and relocated structures.
- Show exact IDs and removal/relocation counts.
- Explicit authorization for reviewed candidate.
- Clearly destructive Apply action.
- Cancel returns without accepted-city changes.

Any changed candidate or removal set invalidates authorization.

Do not silently substitute another destructive candidate on Apply.

### P4.5 Atomic history

Use the existing universal Undo/Redo system.

One demolition-assisted movement equals one atomic transaction.

Undo restores original roads, properties, plots, buildings, metadata, references and relevant history.

Redo restores the exact accepted candidate without rerunning search.

Cancel, failed validation and stale Apply commit nothing.

Save/reopen must preserve valid accepted city.

### P4 gates

- Lightweight preview P95 target 16.7 ms.
- Common complete preview P95 target 250 ms.
- Scheduled slice target 8 ms.
- Responsive cancellation.
- Zero stale results committed.
- Zero partial transactions.
- Demolition may take multiple seconds but must not freeze the interface.
- Report and review unmet performance targets.
