# Universal Adaptive Editing Framework (UAEF) — approved architectural direction
Owner approved discussion 1 on 2026-11-26 Pacific: shared framework with specialized engines, make Mappo as extensible and accessible as possible. This is a planning amendment to the ARES 0.3.0 plan, not approval to start implementation. Finish W4, obtain separate PR163 merge approval, verify exact main, complete the ARES discussions and obtain renewed explicit go-ahead. Existing safety, schema, offline, CI and publishing policies remain unchanged.

## Decisions UAEF-01–08
- UAEF-01: Option B, shared reusable infrastructure and specialized domain engines, not independent duplicated recovery stacks or a universal monolithic geometry solver.
- UAEF-02: Stable versioned typed operation, constraint, dependency, candidate, diagnostics, permission and evidence contracts. Public internal entry points with clear ownership, read-only snapshot input, explicit capabilities and fail-closed incompatible versions. No implicit shared mutable state or direct cross-engine private imports. Reuse existing domain contracts first; avoid wrappers that only duplicate behavior.
- UAEF-03: Cross-engine assistance is mediated by a coordinator, with explicit intent, observable/writable/protected scope, authority, dependencies, bounded work and evidence. A provider cannot silently broaden permissions or recursively start uncontrolled recovery. Cross-domain requests are proposals, never accepted mutations. Future water/terrain editors may invoke road adaptation and SRE through the same contracts once separately approved.
- UAEF-04: Reuse the approved landscape-aware provider registry and independently verified spatial constraint protocol in [ARES-L01–L10](ares-spatial-constraints.md). ARES is the first consumer. No generic constraints bypass domain rules.
- UAEF-05: Shared orchestration, deterministic ranking, work accounting, diagnostics, and incumbent retention; specialized topology, geometry, ownership and recovery algorithms. Extract only reusable responsibilities proven by ARES needs. Record ownership of each layer and avoid circular dependencies.
- UAEF-06: Parallel-ready architecture from the beginning: immutable or isolated snapshots, serializable tasks, deterministic task IDs and ranking, explicit budget ownership and aggregation, cancellation/stale suppression, no wall-clock-driven result selection or shared mutable accepted state. Preserve a serial execution path. Actual multi-worker search scheduling, worker counts, work redistribution, determinism and performance policy require detailed discussion and approval before activation; parallel-ready is not a claim of parallel production execution. Never multiply the approved root budget by number of workers.
- UAEF-07: Central accepted-city authority remains the existing secure identity/transaction host, with independent domain verification, exact Review/Apply, allocation, reversible atomic history, persistence and stale suppression. No engine or worker may publish accepted state directly. Schema 11 and portable/workspace format 1 remain current.
- UAEF-08: Build the minimum reusable seams as ARES needs them during P1–P9. Do not implement speculative future editors, a universal geometry engine, arbitrary third-party runtime code loading, a public plugin marketplace, Steam integration, new schema or full 3D. Separate feature and security approval for any future extension that can execute untrusted code or change accepted data.

## Extensibility and developer accessibility (UAEF-X01–06)
- X01: Clear module boundaries and dependency direction. Document each shared module's responsibility, invariants, inputs/outputs/errors, lifecycle, allowed dependencies, examples and tests. Keep domain-specific policy outside generic orchestration. Use deterministic named registries or explicit composition for providers/strategies; avoid central feature-name switch proliferation where the contract suffices.
- X02: Maintain versioned internal APIs, stable typed references and portable serialized messages; validate at trust boundaries; preserve known metadata and supported saves. Compatibility changes require migration/approval where applicable. No silent fallbacks that bypass safety.
- X03: Provide developer-oriented architecture map, glossary, source navigation, how-to add a provider/strategy/engine adapter, minimal working detached sample and tests, build instructions, offline reproduction and failure diagnosis. Update these with implementation; examples must be verified, not aspirational code presented as working. Keep documentation discoverable from the ARES plan and relevant contributor index.
- X04: Reusable fixture and contract-test harness; a synthetic provider and strategy can be added without modifying central coordinator/search logic, demonstrate deterministic ordering, budget/cancel/stale propagation, independent verification and refusal for missing authority. A fake second domain adapter demonstrates the seam without claiming a real water/terrain editor. No expansion of write permissions.
- X05: Keep modular source and reproducible single-file HTML distribution. No required server, runtime network dependency, paid API or new build tool merely to use Mappo. Developer workflow should be approachable with documented commands and actionable CI diagnostics; preserve GitHub-first qualification.
- X06: Document extension limits, capability flags, supported versions, failure cases and policy boundaries. Internal extension seams are not a stable public SDK, arbitrary executable plugin interface or license change; those require separate design decisions.

## End-user accessibility and performance (UAEF-A01–06)
- A01: Progressive disclosure: simple safe defaults, understandable Strict/Adaptive/Restructure controls, optional advanced controls; explain permission consequences and actual affected objects. Do not require technical engine knowledge or mandatory tutorials. No automatic destructive escalation.
- A02: Keyboard-operable controls and existing numeric road edits, clear focus order and visible focus, meaningful labels/accessible names and status announcements; avoid duplicate live regions. Support mouse/trackpad and existing desktop shortcuts. Where canvas interaction requires alternative selection/input, use existing or approved accessible equivalent and report gaps explicitly rather than claim complete accessibility.
- A03: Do not rely on color alone for road/retirement/restore/conflict state; use text and/or distinct visual markers, readable contrast and understandable feedback. Test review, cancellation, refusal and permission flow without relying on color. Respect supported zoom/layout and avoid clipping important controls.
- A04: Maintain responsive desktop editing, offline Firefox/Chromium, normal desktop and ultrawide layouts; keep cancellation and UI interaction available during expensive work. Prefer bounded memory and CPU use, serial fallback and transparent capability limits on less powerful desktop hardware. Benchmark representative low-resource configurations before any new minimum system requirement. No promise of phone/tablet support, all-device performance or formal accessibility conformance; those require separate scope and evidence.
- A05: Clear progress, actionable blocker explanations, exact changes and explicit consent; no jargon-only refusals. Use work-unit progress rather than fabricated ETA; distinguish blocked, unsupported, canceled, exhausted and verified states.
- A06: Include keyboard-only controls, focus restoration, labels/status, non-color indicators, layout/zoom, offline and responsive operation in P8/P9 acceptance. Use automated checks and representative hands-on testing, report limitations. Existing regression and geometry safety gates remain mandatory. No claims of WCAG certification or universal usability without dedicated evidence.

## Phase integration
P1 maps contract boundaries, ownership, versioning, user-facing diagnostics and glossary. P2 proves provider registry and dependency discovery against actual model and synthetic adapters. P3 designs serial/parallel-ready task and budget seams, deterministic ranking, fixtures and reproducibility. P4–P6 implement specialized road topology and ownership without generic layers absorbing domain policy. P7 composes specialized adapters and demonstrates a synthetic second domain/strategy through contracts, with independent verification and unchanged accepted state. P8 mounts offline UI and accessibility requirements; document and test keyboard/numeric paths, focus, readable review, cancellation and permissions. P9 qualifies existing 10,000-scenario corpus plus extension contracts, representative desktop/ultrawide Firefox/Chromium and accessible controls, documented reproducible examples, performance limitations and complete existing CI. Do not reduce existing test coverage or acceptance thresholds. No new parallel feature workstream.
