# DEV-OPT research operations

Development-only; no runtime bundling or authority to adopt a candidate. Use the exact source revision of a separately authorized experiment and retain all original evidence. Do not submit arbitrary third-party or unreviewed code. All hosted research workflows use contents read, no persisted credentials, fixed Node 22, and explicit commit markers. Separate target checkout is not a security sandbox.

## SRE research

1. Start an isolated research/sre/<request> branch from a reviewed harness revision containing the workflow. The existing DEV-OPT draft branch also supports the marker. Do not push directly to main or modify the product SRE branch for research submissions.
2. Update docs/development/research/sre-submission.json with the owner-authorized immutable target SHA, 2–4 allowlisted schedules and 2–4 bounded cases. Existing historical controls apply only when their expectations remain valid for the target. Preserve an exact manifest/revision per run; do not silently tune against held-out cases. A new city fixture is allowed only within the validated scope. No regeneration; existing 32M/131072 per-solve budget unchanged.
3. Push explicit [sre-research-pilot] commit. Two hosted shards execute tasks sequentially per shard; aggregate exact same-attempt artifacts, project and operation identity, verified candidate gates and deterministic replay. A valid exploratory refusal is not a recovered candidate. Missing or invalid evidence cannot pass. Inspect report, original diagnostics, manifest and GitHub run/job IDs; retain important evidence beyond default 14-day artifact retention by recording results at exact source revision.
4. Compare verified outcomes within the same case and budget; report retirement counts, demolished footprint, scaling, work, elapsed time and memory separately. Do not treat different environments as a controlled speedup or automatic adoption. Preserve historical controls and holdout limitations. Any new strategy implementation or production adoption must be within separate approved scope and pass normal CI/manual gates.

The two fixed qualification workflows [research-pilot] and [diagnostics-pilot] remain restricted to the DEV-OPT draft branch. They are not general research submission services. Ordinary CI diagnosis: `node scripts/development/research/ci-diagnostics.mjs RUN_ID SHA ATTEMPT NEW_OUTPUT_DIRECTORY` with authenticated read-only GitHub CLI; expected nonzero on original failure, even if report generation succeeds. Read the original logs and provisional classification; never print raw terminal controls. No automatic repairs. No automatic per-failure workflow trigger in current scope. Additional domain adapters follow domain implementation and approval. No runner pool or application behavior change.
